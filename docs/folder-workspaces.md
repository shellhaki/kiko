# Folder workspaces

Owner-directed product change, November 9, 2026. This supersedes the original virtual-project creation flow and the earlier rule that project folders never map to disk.

Choose **This workspace** in the desktop composer, then select an existing folder. Kiko uses its canonical path as the project root and its folder name as the initial project name. Selecting the same folder reuses its project. New chats in that project inherit the root. Chats without a folder remain ordinary local conversations. Existing virtual projects and their content remain available; select a folder to connect one of their chats. There is no New project form or duplicate empty-state creation button.

The folder selector changes the current chat's root only while no reply is running and before that chat has written project files. A chat with files keeps its root: start a new chat to work elsewhere. Selecting a folder for a chat with existing editable artifacts also saves their source copies there. Selecting a folder from Home carries the draft into the new project context. Cancelling the native picker leaves the current context intact.

## Files and the editor

`list_files`, `read_file`, `write_file`, and `delete_file` are original Go tools, following familiar agent file-operation patterns. They are offered to the model only when the current chat has a selected root. They execute in Go; the model receives schemas and results. There is no copied Claude or Codex implementation, SDK, subprocess agent, or additional agent subscription.

Paths are relative to the selected root. `/docs/plan.md` means `<selected folder>/docs/plan.md`; it never means the machine's `/docs`. Nested folders are created when a file write needs them. Reads/writes accept UTF-8 text up to 1 MB. Listings are limited to 500 immediate entries. Existing text files require the SHA-256 hash returned by `read_file`; a missing or stale hash refuses replacement. Go `os.Root` enforces the root boundary, including symlinks leading outside it. Traversal and common sensitive metadata paths are refused. No shell, process execution, unrestricted filesystem access, or arbitrary network tool is provided. File deletion is available only through `delete_file`, which requires the file's current hash and always pauses for user approval.

Editable documents keep their structured revisions and drafts in SQLite and save Markdown copies into the selected folder. Sheets and decks save `.sheet.json` and `.deck.json` source files; XLSX, CSV, PPTX, DOCX, and PDF remain explicit exports. The New artifact form and `create_document`, `create_sheet`, and `create_deck` tools accept a full root-relative source path, such as `docs/plan.md`, `docs/budget.sheet.json`, or `docs/launch.deck.json`. Omitted paths use a readable title and stable artifact ID. Paths are reserved before the first write so a failed disk save retains the intended destination. Existing files and other artifact paths cannot be claimed by new artifact creation. Existing external edits refuse replacement on the next changed save. Generic `write_file` cannot overwrite an editor-owned source file; the agent must use the corresponding document/sheet/deck tools.

SQLite saves and filesystem writes are separate operations. If the folder is unavailable, permission is declined, or a disk copy conflicts, the editable content remains in Kiko. The conversation shows a real folder-save issue with **Retry folder save**. A retry rechecks the file hash; it cannot silently replace external edits. Disk files are never automatically loaded over current editor content. Other text files appear in the chat and open in an editable pane beside it. Generated artifact cards appear with their creating reply; older or manually created artifacts remain under **Files in this chat**.

Removing a chat/project or resetting Kiko removes its database metadata and saved grants, not files in selected folders. Kiko does not recursively erase a project directory.

## Explorer, imports, and external changes

A selected project's sidebar includes a collapsible Files explorer. It lists real directories on demand, sorts folders before files, refreshes expanded directories while the app is visible, and offers manual refresh. It does not recursively index the entire root. The existing 500-entry directory limit and excluded sensitive/symlink paths apply.

Opening an ordinary text file shows its contents beside chat. Typing persists a local SQLite draft after a short debounce; Save, the standard save shortcut, or guarded navigation flushes a hash-checked disk write. A failed write preserves the draft. Reopening the file recovers its text and original baseline hash, including after a restart. Workspace file drafts are removed with project metadata on reset, while external disk files remain.

Markdown, `.sheet.json`, and `.deck.json` files can be opened as editable artifacts. This creates a local structured record linked to the existing path, leaving the disk file untouched. Reopening a linked file selects its owning chat/editor rather than duplicating the artifact. Imports validate the supported Markdown/artifact format and preserve project-Home drafts when creating a chat. Unsupported content stays available in the text editor. Deck image references must belong to the importing chat.

Open files and linked sources are checked for external changes while visible. Kiko retains the current editor contents and offers a side-by-side comparison. **Load folder version** checks the compared file hash and local artifact revision before creating a local revision; recovered drafts and active replies must be resolved first. **Save Kiko version** or **Save my draft** explicitly replaces the compared disk version using its current hash. A changed file or revision refuses the action and requires another comparison. Missing artifact source files can be recreated only by an explicit comparison action. This is a guarded choice between versions, not automatic merging or an operating-system file watcher. Raw text files do not yet have a revision-history browser.

Direct file writes recheck the file's artifact ownership and proposed source content before applying. Importing a file into an editor, or changing an artifact while its copy is being written, cannot make an older write overwrite the newer state.

## Permissions

File writes inside the selected root apply directly as basic document CRUD: reading/listing within a user-selected root is allowed, and each model-requested write goes through immediately. The path boundary, hash guards, and overwrite guards still apply. There is no shell or access to other directories, and no per-write approval step. Only `delete_file` pauses for approval: the agent must supply the hash from `read_file`, the run waits for the user's decision on a small composer-anchored popover, and a denial ends the deletion without retry. File writes stream visible per-file progress: each file gets its own step showing its path and received size while it streams in, then a Wrote confirmation, with files completing one at a time in order. The agent works self-directed within a command: it states a brief plan, decides structure and wording itself, records material assumptions as it goes, and summarizes at the end. Verifiable facts it was not given become [NEEDS: ...] markers in the text, never guesses; questions are reserved for user-owned facts or true forks. Document side previews stay closed while drafting: a document reveals only when its last pending section is filled (or immediately when created complete), each finished document appearing in turn. Document edits apply directly with no review step: there is no suggestion mode, no proposal queue, and no accept/reject permissions for modifying documents. Deleting a document, sheet, or deck uses `delete_document`/`delete_artifact` with the same approval pause, guarded to the owning chat; the open pane closes and linked workspace file records are unlinked while disk files stay in place. The only way the agent asks for anything is the anchored comment question in chat, which the user answers in conversation. The proposals storage API remains as inert schema with passing tests. Manual editor changes and explicit retry clicks authorize their own source-copy saves.

File contents and tool results can contain sensitive user material. They are stored in the local database; tool results needed by the agent are sent to the selected model. A selected folder is a grant to read its ordinary files on request, not an instruction to index or upload the entire tree.

## Desktop and web

The native folder picker belongs to the Wails desktop adapter. Web mode disables choosing local project folders and exposes no RPC accepting arbitrary server paths. Attachments still import through the composer plus button, including from Home, and do not require a project folder. The web adapter can display already configured folder metadata and uses the same confined file tools for chats that already have a server-side root; it does not turn a browser upload into a local filesystem grant.

## Motion and startup

The initial splash has a three-second minimum and continues while initialization is pending. It uses an indeterminate indicator rather than a fabricated percentage. Sidebar content stays mounted while its width, opacity, and position transition, and becomes inert when collapsed. Direct pane dragging remains immediate. Chat follow/jump scrolling is smooth and gives control back to manual wheel/touch/scroll-key input. Scrolling respects reduced motion. Typing updates immediately; draft persistence is coalesced over 200 ms and flushed before send/import/folder changes and on conversation unmount.

## Reference and remaining scope

[Codex's workspace-write description](https://github.com/openai/codex/blob/main/codex-rs/prompts/templates/permissions/sandbox_mode/workspace_write.md) was reviewed as a boundary-design reference. Kiko's implementation is independent and deliberately limited to the tools above. Broader terminal tools, outside-root access, automatic merging, directory relocation/reconnection, and richer search/move/rename tools require separate scope and tests. The design-system document remains pending the owner's visual approval of the remodel.
